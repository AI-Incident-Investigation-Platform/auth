# Устройство auth

## Вход по коду

Пароля нет: вход и регистрация — один поток `login` → `otp/verify`.

- **Challenge** — ключ `auth:otp:<challenge_id>` в Dragonfly со сроком
  `otp_challenge_ttl_seconds`: email, HMAC-SHA256 digest кода, срок кода,
  время, с которого разрешён повтор, число повторов. Сам код нигде не
  хранится. Ключ HMAC выводится из ключа подписи JWT: дамп кэша без него
  не перебрать за 10^6 шагов.
- **Попытки** — отдельный счётчик `auth:otp:<challenge_id>:attempts`
  (`INCR`): параллельные догадки не обходят лимит. Последняя неверная
  попытка удаляет challenge.
- **Одноразовость** — верный код удаляет challenge; сессию открывает только
  тот из параллельных `verify`, чей `DEL` удалил ключ.
- **Аккаунт** создаётся в `verify`, если email новый. Неподтверждённых
  аккаунтов нет. Параллельные `verify` двух challenge одного нового email
  создают одного пользователя: второй ловит `uq_users_email` и читает
  существующего.
- **Лимит писем** — счётчик `auth:otp-sends:<sha256(email)>` на час.
  Лимита по IP нет: на маке у всех запросов один адрес балансировщика.
- **Письмо** — задача `auth.login_code` в exchange `email` (direct,
  durable) с routing key `send.transactional`: `message_id`, `to`,
  `locale`, `params` (`code`, `expires_in`), `expires_at`, TTL сообщения —
  срок кода, `traceparent` в заголовках. Публикация `mandatory` с
  подтверждением брокера: `202` уходит после подтверждения. Брокер
  недоступен или очереди-получателя нет — `503`, challenge удаляется.
  Соединение с RabbitMQ открывается при первой публикации и
  переподключается само; `/ready` брокер не проверяет: без него не работает
  только запрос кода, а сессии, refresh и `/me` продолжают работать.
- Код и `challenge_id` в логи не пишутся.

## Токены и сессии

Каждый вход — отдельная сессия (устройство): строка в таблице `session` с
хэшем refresh-токена и `user_agent`.

- **Access** — RS256 JWT на 15 минут, ключ из `keys/private.pem`. Claims:
  `sub` (id пользователя), `sid` (id сессии), `iss=auth`, `aud=aiip`,
  `iat`, `exp`. Ролей в токене нет: `auth` знает, кто пользователь, а права
  на объекты каждый сервис проверяет по своим данным.
- **Пропуск сессии** — ключ `auth:session:<sid>` в Dragonfly. Живёт как
  access-токен и выставляется при каждой его выдаче. Это публичный контракт
  `auth`: любой сервис проверяет запрос так — подпись и claims по JWKS,
  затем `EXISTS auth:session:<sid>`; ключа нет — 401, кэш недоступен —
  отказ. Выход и кража refresh удаляют ключ, поэтому отзыв
  мгновенный на всех сервисах. Хранятся живые сессии, а не отозванные:
  вытесненный кэшем ключ даёт 401 и восстанавливается refresh'ем, а не
  пропускает отозванный токен.
- **Refresh** — случайная строка `<sid>.<secret>`, в БД — хэш. Живёт 30
  дней от последнего обновления и ротируется при каждом `refresh`.
  Предыдущий токен 10 секунд после ротации считается соседней вкладкой: по
  нему выдаётся только access. Позже — кража, сессия отзывается.
- **Куки** — `HttpOnly`, `SameSite=Strict`: access на `Path=/` (видят все
  сервисы за gateway и WebSocket), refresh на `Path=/api/v1/auth`. В теле
  ответа токенов нет. Между сервисами токен идёт в `Authorization: Bearer`.
- **CSRF** — `OriginMiddleware`: изменяющий запрос к `/api` без `Origin`
  из `auth.allowed_origins` получает `403`. Запрос с `Authorization`
  (вызов сервиса) не проверяется.
- Выход закрывает текущую сессию. Блокировки пользователей и списка
  устройств пока нет.

## Код

```
src/
├── main.py              сборка: DI, lifespan (конфиг → ключ), middleware, роутеры, ошибки, трейсинг
├── config/              Config (pydantic-settings), доступ через `from src.config import cfg`
├── api/
│   ├── auth/            service.py и dto.py общие для всех версий
│   │   └── v1/          HTTP-форма v1: router, schemas, cookies — вход по коду, refresh, logout, /me
│   ├── health/          /health и /ready вне /api
│   ├── jwks/            /.well-known/jwks.json вне /api, без версии
│   ├── metrics/         /metrics вне /api
│   └── exc/             ApiErrorHandler и ошибки домена auth
└── core/
    ├── admission/       предел одновременных запросов пода → 503 с Retry-After
    ├── errors/          категории ошибок, ErrorReport
    ├── db/              модели user и session, DTO, репозитории, UnitOfWork
    ├── security/        JWT, JWKS, коды входа и их challenge, пропуска сессий, Origin, CurrentUser
    ├── email/           задачи сервису email в RabbitMQ
    ├── cache/           клиент Dragonfly
    ├── di/              провайдеры dishka
    └── logging.py, tracing.py, metrics.py, middleware.py, context.py
```

Тесты: `tests/unit` без внешних зависимостей, `tests/integration` —
Postgres и Dragonfly в Testcontainers.

## Версии API

Публичный путь — `/api/v<N>/auth/...`, как в контракте продукта (12 §3).

- Версия только мажорная. Внутри версии контракт расширяется обратно
  совместимо: новое поле опционально, старые не удаляются и не меняют
  смысл. Ломающее изменение — новая версия.
- Версия живёт только в HTTP-слое: `src/api/auth/v<N>/` — router, schemas,
  cookies. `AuthService`, DTO и `core/` версий не знают, поэтому две версии
  одновременно — это два роутера над одним use-case.
- Корневой роутер собирает `/api` → `/v<N>` → домены. У каждой версии свой
  путь в Ingress, неизвестная версия отвечает 404 на gateway.
- Без версии — служебные роуты и JWKS (`/.well-known/jwks.json`, RFC 8615):
  ключи сменяются через `kid`, а не через адрес.
- Метка `path` метрик — шаблон маршрута с версией, поэтому трафик каждой
  версии виден в Grafana.

Как выпустить v2:

1. Скопировать `v1/` в `v2/`, поменять в нём то, что ломает контракт;
   общую логику — в сервисе.
2. Подключить `v2` в `src/api/__init__.py` и добавить путь `/api/v2/auth`
   в Ingress.
3. Роутер v1 начинает отдавать `Deprecation` (RFC 9745), `Sunset`
   (RFC 8594) и `Link: <...>; rel="successor-version"`.
4. Когда трафик v1 в метриках упал до нуля и дата `Sunset` прошла — удалить
   `v1/`, его подключение и путь в Ingress.

Кука refresh лежит на `Path=/api/v1/auth`, на `/api/v2/auth` браузер её не
пришлёт. Если v2 меняет `refresh` или `logout`, на время перехода оба
роутера выставляют refresh-куку на пути обеих версий; иначе выход v2 —
повторный вход у всех пользователей.

## Наблюдаемость

- Логи — JSON в stdout: `timestamp`, `level`, `message`, `service`,
  `trace_id`.
- Трейсы — OTLP в `alloy.infra:4318`, ресурс `service.name=auth`;
  инструментированы FastAPI, SQLAlchemy, redis-клиент.
- Метрики на `/metrics`: `http_requests_total`,
  `http_request_duration_seconds`, `http_requests_active`,
  `http_requests_capacity` и метрики процесса.
- `trace_id` уходит наружу как `X-Request-ID` и `request_id` в ошибке.

## Ресурсы и масштабирование

- Под: `requests` 100m / 160Mi, `limits` 1000m / 256Mi. Память ~120 МиБ в
  простое, ~160 МиБ на пике. В образе `MALLOC_ARENA_MAX=2` и
  `MALLOC_MMAP_THRESHOLD_=131072`: RSS меньше на 30–35%.
- Число подов — KEDA (`k8s/scaledobject.yaml`), 1–3 пода. Триггеры: CPU
  процесса из Prometheus (0,5 ядра на под), насыщение — активные запросы к
  `http_requests_capacity` (0,5), CPU по metrics-server как запасной. Если
  метрики недоступны — 2 пода. Поля `replicas` в Deployment нет.
- Сверх 32 одновременных запросов под отвечает 503 с `Retry-After`, а не
  копит очередь.
- Пул Postgres: `pool_size` 5 + `max_overflow` 5, таймаут получения 2 с.
- Стоимость: `refresh` ~10 мс CPU, `/me` ~3 мс. Замеры пропускной
  способности сделаны до входа по коду (тогда вход стоил ~30 мс Argon2):
  ~100–130 запросов/с на под, упор в event loop Python. Вход по коду не
  замерен.
- Выкатка: миграции Job'ом, затем RollingUpdate с `maxUnavailable: 0`; не
  стали готовы — `make up` делает `rollout undo`.

## Решения

- **Токен проверяет каждый сервис сам, а не gateway** (2026-10-22).
  Сервисы зовут друг друга мимо Traefik, так что проверка в сервисах нужна
  в любом случае; ForwardAuth добавил бы поход в `auth` на каждый запрос и
  сделал его точкой отказа всей системы.
- **Мгновенный отзыв через пропуск живой сессии в кэше** (2026-10-22):
  одна проверка в кэше на запрос вместо похода в `auth`.
- **Вход без пароля, по коду на почту** (2026-10-27). Одно окно входа и
  регистрации, аккаунт создаётся подтверждённым кодом email. Пароль,
  Argon2 и смена пароля удалены. Отброшены пароль + OTP (лишний шаг без
  выигрыша: доступ к почте и так даёт вход) и отдельная регистрация с
  неподтверждёнными аккаунтами.
- **Сессия только в HttpOnly-куках** (2026-10-27): токен недоступен JS, так
  что XSS не может его унести; WebSocket авторизуется той же кукой. Цена —
  CSRF-защита по `Origin` на каждом изменяющем запросе. Отброшен access в
  теле ответа и памяти браузера с WS-ticket.
- **Письма — через RabbitMQ в сервис `email`** (2026-10-27): `auth` не
  зависит от скорости и доступности почтового провайдера, `email`
  масштабируется по очереди. Отброшена синхронная отправка из `auth`.
- **Challenge и лимиты — в Dragonfly, а не в Postgres** (2026-10-27): они
  живут минуты и умирают по TTL. Dragonfly работает в режиме кэша и может
  вытеснить ключ — тогда пользователь запросит код заново.
- **Ошибки — конверт `{"error": {...}}` из контракта продукта**
  (2026-10-27) вместо `application/problem+json`: у всех сервисов за
  gateway одна форма ошибки.
- **Гибкость вместо ресурсов** (2026-10-25): на одной ноде живёт до ~12
  сервисов, поэтому у пода дешёвые `requests`, предел одновременных
  запросов и автоскейлинг KEDA 1–3 по нагрузке. Прежние схемы — HPA 1–4 по
  CPU и один под в жёстких рамках — отброшены.

- **Версия в пути перед сервисом: `/api/v1/auth`** (2026-10-25). Так
  требует контракт продукта, фронт получает ровно описанные адреса.
  Отброшен вариант `/api/auth/v1`: кука refresh на `/api/auth` пережила бы
  смену версий, а Ingress не менялся бы, но это расхождение с контрактом.
  Цена выбора — переходный период для куки при v2, см. «Версии API».
- **JWKS без версии и вне `/api`** (2026-10-25): его читают только сервисы
  внутри кластера, браузеру он не нужен; формат JWKS задан RFC 7517 и
  версией API не меняется.

## Чего пока нет

- Колонка `users.password_hash` осталась (теперь nullable): удаляется
  следующим релизом, когда старая версия кода с паролем больше не работает.
- Rate limit по IP клиента: на маке Traefik видит у всех запросов адрес
  балансировщика k3d, поэтому лимит общий на всех.
- Сессий для сервисов (service identity) — см.
  [requirements.md](requirements.md).
