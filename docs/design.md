# Устройство auth

## Вход по коду

Пароля нет. Три потока на одном механизме кода: регистрация
`register` → `otp/verify`, вход `login` → `otp/verify`, смена почты
`email/change` → `email/change/verify`. Challenge помнит, для чего выдан
(`purpose`), и чужая ручка его не принимает.

- **Challenge** — ключ `auth:otp:<challenge_id>` в Dragonfly со сроком
  `otp_challenge_ttl_seconds`: назначение, email, HMAC-SHA256 digest кода,
  срок кода, время, с которого разрешён повтор, число повторов; у смены
  почты ещё `user_id`, новая почта и digest второго кода. Второй код
  хэшируется с другой солью (`<challenge_id>:new`), поэтому коды двух почт
  не взаимозаменяемы. Сам код нигде не
  хранится. Ключ HMAC выводится из ключа подписи JWT: дамп кэша без него
  не перебрать за 10^6 шагов.
- **Попытки** — отдельный счётчик `auth:otp:<challenge_id>:attempts`
  (`INCR`): параллельные догадки не обходят лимит. Последняя неверная
  попытка удаляет challenge.
- **Одноразовость** — верный код удаляет challenge; сессию открывает только
  тот из параллельных `verify`, чей `DEL` удалил ключ.
- **Аккаунт** создаётся в `verify` кода регистрации. Неподтверждённых
  аккаунтов нет. Параллельные `verify` двух регистраций одной почты
  создают одного пользователя: второй ловит `uq_users_email` и получает
  `409 auth.email_taken`.
- **Событие `user.registered`** публикуется в topic exchange `auth.events`
  до commit, `mandatory` и с подтверждением брокера: не подтверждено —
  аккаунт не создаётся, `503 events.unavailable`. Так у пользователя всегда
  будет профиль в `users`. Обратный сбой — событие ушло, а commit не
  прошёл — оставляет в `users` профиль без аккаунта; войти в него нельзя.
- **Смена почты** — под блокировкой строки пользователя: почта меняется,
  остальные живые сессии отзываются вместе с пропусками в кэше,
  `user.email_changed` публикуется до commit. Письмо старой почте — после
  commit и без отката при сбое: почта уже сменена.
- **Лимит писем** — счётчик `auth:otp-sends:<sha256(email)>` на час.
  Лимита по IP нет: на маке у всех запросов один адрес балансировщика.
- **Письмо** — задача `auth.login_code`, `auth.register_code`,
  `auth.email_change_current_code` или `auth.email_change_new_code` в
  exchange `email` (direct, durable) с routing key `send.transactional`:
  `message_id`, `to`, `locale`, `params` (`code`, `expires_in`, у смены
  почты на текущий адрес — `new_email`), `created_at`, `expires_at`,
  `collapse_key` `<шаблон>:<email>` (новый код на тот же адрес снимает
  ждущее письмо со старым), TTL сообщения — срок кода, `traceparent` в заголовках. Публикация `mandatory` с
  подтверждением брокера: `202` уходит после подтверждения. Брокер
  недоступен или очереди-получателя нет — `503`, challenge удаляется.
  Соединение с RabbitMQ открывается при первой публикации и
  переподключается само; `/ready` брокер не проверяет: без него не работает
  только запрос кода, а сессии, refresh и `/me` продолжают работать.
- Код и `challenge_id` в логи не пишутся.

## Токены и сессии

Каждый вход — отдельная сессия (устройство): строка в таблице `session` с
хэшем refresh-токена и `user_agent`.

- **Access** — RS256 JWT на 15 минут, ключ из `keys/private.pem`. Claims:
  `sub` (id пользователя), `sid` (id сессии), `iss=auth`, `aud=aiip`,
  `iat`, `exp`. Ролей в токене нет: `auth` знает, кто пользователь, а права
  на объекты каждый сервис проверяет по своим данным.
- **Пропуск сессии** — ключ `auth:session:<sid>` в Dragonfly. Живёт как
  access-токен и выставляется при каждой его выдаче. Это публичный контракт
  `auth`: любой сервис проверяет запрос так — подпись и claims по JWKS,
  затем `EXISTS auth:session:<sid>`; ключа нет — 401, кэш недоступен —
  отказ. Выход и кража refresh удаляют ключ, поэтому отзыв
  мгновенный на всех сервисах. Хранятся живые сессии, а не отозванные:
  вытесненный кэшем ключ даёт 401 и восстанавливается refresh'ем, а не
  пропускает отозванный токен.
- **Refresh** — случайная строка `<sid>.<secret>`, в БД — хэш. Живёт 30
  дней от последнего обновления и ротируется при каждом `refresh`.
  Предыдущий токен 10 секунд после ротации считается соседней вкладкой: по
  нему выдаётся только access. Позже — кража, сессия отзывается.
- **Куки** — `HttpOnly`, `SameSite=Strict`: access на `Path=/` (видят все
  сервисы за gateway и WebSocket), refresh на `Path=/api/v1/auth`. В теле
  ответа токенов нет. Между сервисами токен идёт в `Authorization: Bearer`.
- **CSRF** — `OriginMiddleware`: изменяющий запрос к `/api` без `Origin`
  из `auth.allowed_origins` получает `403`. Запрос с `Authorization`
  (вызов сервиса) не проверяется.
- Выход закрывает текущую сессию. Блокировки пользователей и списка
  устройств пока нет.

## Версии API

Публичный путь — `/api/v<N>/auth/...`, как в контракте продукта (12 §3).

- Версия только мажорная. Внутри версии контракт расширяется обратно
  совместимо: новое поле опционально, старые не удаляются и не меняют
  смысл. Ломающее изменение — новая версия.
- Версия живёт только в HTTP-слое: `src/api/auth/v<N>/` — router, schemas,
  cookies. `AuthService`, DTO и `core/` версий не знают, поэтому две версии
  одновременно — это два роутера над одним use-case.
- Корневой роутер собирает `/api` → `/v<N>` → домены. У каждой версии свой
  путь в Ingress, неизвестная версия отвечает 404 на gateway.
- Без версии — служебные роуты и JWKS (`/.well-known/jwks.json`, RFC 8615):
  ключи сменяются через `kid`, а не через адрес.
- Метка `path` метрик — шаблон маршрута с версией, поэтому трафик каждой
  версии виден в Grafana.

Как выпустить v2:

1. Скопировать `v1/` в `v2/`, поменять в нём то, что ломает контракт;
   общую логику — в сервисе.
2. Подключить `v2` в `src/api/__init__.py` и добавить путь `/api/v2/auth`
   в Ingress.
3. Роутер v1 начинает отдавать `Deprecation` (RFC 9745), `Sunset`
   (RFC 8594) и `Link: <...>; rel="successor-version"`.
4. Когда трафик v1 в метриках упал до нуля и дата `Sunset` прошла — удалить
   `v1/`, его подключение и путь в Ingress.

Кука refresh лежит на `Path=/api/v1/auth`, на `/api/v2/auth` браузер её не
пришлёт. Если v2 меняет `refresh` или `logout`, на время перехода оба
роутера выставляют refresh-куку на пути обеих версий; иначе выход v2 —
повторный вход у всех пользователей.

## Наблюдаемость

- Логи — JSON в stdout: `timestamp`, `level`, `message`, `service`,
  `trace_id`.
- Трейсы — OTLP в `alloy.infra:4318`, ресурс `service.name=auth`;
  инструментированы FastAPI (без внутренних спанов ASGI `receive`/`send`),
  SQLAlchemy, redis-клиент.
- Метрики на `/metrics`: `http_requests_total`,
  `http_request_duration_seconds`, `http_requests_active`,
  `http_requests_capacity` и метрики процесса.
- `trace_id` уходит наружу как `X-Request-ID` и `request_id` в ошибке.

## Ресурсы и масштабирование

- Под: `requests` 100m / 160Mi, `limits` 1000m / 256Mi. Память ~125 МиБ в
  простое, до ~170 МиБ под нагрузкой. В образе `MALLOC_ARENA_MAX=2` и
  `MALLOC_MMAP_THRESHOLD_=131072`: RSS меньше на 30–35%.
- Число подов — KEDA (`k8s/scaledobject.yaml`), 2–3 пода: второй под
  держит вход, пока первый перезапускается или выкатывается. Триггеры: CPU
  процесса из Prometheus (0,5 ядра на под), насыщение — активные запросы к
  `http_requests_capacity` (0,5), CPU по metrics-server как запасной. Если
  метрики недоступны — 2 пода. Поля `replicas` в Deployment нет.
- Сверх 64 одновременных запросов под отвечает 503 с `Retry-After`, а не
  копит очередь.
- Пул Postgres: 10 постоянных соединений без `max_overflow`, таймаут
  получения 2 с, без `pool_pre_ping`, пересоздание раз в 30 минут. Три пода —
  30 соединений из 300 `max_connections` Postgres.
- Замер 2026-10-27, вход по коду, трейсинг 100%, генератор в кластере мимо
  Traefik с постоянной частотой запросов. CPU на запрос: `/me` ~2 мс,
  `refresh` ~2,6 мс, `login` ~2,2 мс, `login` + `otp/verify` ~7 мс. Под
  упирается в одно ядро (event loop Python, совпадает с `limits.cpu`) и
  без ошибок держит около: `/me` 450/с, `refresh` 330/с, `login` 470/с,
  полный вход 140/с, смесь 70% `/me` / 20% `refresh` / 10% входа 380/с.
  Три пода — смесь ~860/с. Дальше под отвечает 503, без OOM и
  перезапусков.
- Замер 2026-10-29 через Traefik, как ходит браузер: разгон до 600/с,
  смесь с полным входом, KEDA 2–3 пода, трейсинг 100%. Под держит ~220/с
  при 0,75 ядра, три пода — ~650/с, дальше 503 (2,4% запросов на пике).
  Удаление пода под 300/с проходит без ошибок. Хвосты сверх этого — паузы
  ввода-вывода Docker-диска на маке (PSI io 50–80%), а не процесса.
- Замер 2026-10-29 на очищенном Docker-диске, через Traefik, та же смесь,
  число подов зафиксировано, нагрузка растёт линейно за 5 минут. Без ошибок
  и с p95 < 50 мс: один под ~340/с (потолок ~430/с, под упирается в ядро),
  два — ~460/с (потолок ~600/с), три — ~500/с (потолок ~700/с). Два и три
  пода упираются в общие 8 ядер ноды, которые делят генератор нагрузки,
  Traefik и наблюдаемость: под на пике занят на 0,85 ядра. При обычной
  нагрузке в обработке одновременно 3–5 запросов на под, потолок —
  предел одновременных запросов. Перезапусков подов нет.
- Трейсинг 100% стоит ~15% CPU пода (`/me` + `refresh` 250/с через
  Traefik: 0,50 ядра против 0,43 без трейсинга). Почти всё — сама
  инструментация на каждом запросе, а не экспорт: доля 10% экономит
  единицы процентов. Доля задаётся без пересборки:
  `OTEL_TRACES_SAMPLER=parentbased_traceidratio`,
  `OTEL_TRACES_SAMPLER_ARG=<доля>`; через Traefik решает его
  `tracing.sampleRate`, auth следует родителю.
- Сборка мусора: после старта `gc.collect()` и `gc.freeze()` — ~167 тыс.
  объектов старта уходят в постоянное поколение. Без этого полная сборка
  обходила их под нагрузкой и останавливала event loop на 60–170 мс, а за
  паузу при 250/с копилось больше 32 запросов — 503 при CPU пода 0,6.
- uvicorn с uvloop и httptools вместо asyncio и h11: CPU пода меньше ~8%.
- Выкатка: миграции Job'ом, затем RollingUpdate с `maxUnavailable: 0`; не
  стали готовы — `make up` делает `rollout undo`.

## Решения

- **Токен проверяет каждый сервис сам, а не gateway** (2026-10-22).
  Сервисы зовут друг друга мимо Traefik, так что проверка в сервисах нужна
  в любом случае; ForwardAuth добавил бы поход в `auth` на каждый запрос и
  сделал его точкой отказа всей системы.
- **Мгновенный отзыв через пропуск живой сессии в кэше** (2026-10-22):
  одна проверка в кэше на запрос вместо похода в `auth`.
- **Вход без пароля, по коду на почту** (2026-10-27). Аккаунт создаётся
  подтверждённым кодом email. Пароль, Argon2 и смена пароля удалены.
  Отброшены пароль + OTP (лишний шаг без выигрыша: доступ к почте и так
  даёт вход) и регистрация с неподтверждёнными аккаунтами.
- **Регистрация отдельно от входа, `auth` — только вход** (2026-10-30).
  После регистрации человек заполняет профиль, а профиль — забота сервиса
  `users`; `auth` хранит только id и почту и сообщает о них событиями.
  Скрывать, зарегистрирована ли почта, продукт не требует: `register` на
  занятую почту — `409`, `login` на незнакомую — `404`. Отброшены одно
  окно для обоих (было до этого решения) и синхронный вызов `users` при
  регистрации (регистрация зависела бы от доступности второго сервиса).
- **Смена почты двумя кодами** (2026-10-30): почта и есть аккаунт, и одной
  украденной сессии не должно хватать, чтобы его увести. Отброшен один код
  на новую почту с письмом-предупреждением на старую.
- **Событие до commit, а не outbox** (2026-10-30): подтверждение брокера
  уже есть у писем, отдельная таблица outbox и её разборщик — лишний
  процесс. Цена — редкий профиль без аккаунта в `users` при сбое commit.
- **Сессия только в HttpOnly-куках** (2026-10-27): токен недоступен JS, так
  что XSS не может его унести; WebSocket авторизуется той же кукой. Цена —
  CSRF-защита по `Origin` на каждом изменяющем запросе. Отброшен access в
  теле ответа и памяти браузера с WS-ticket.
- **Письма — через RabbitMQ в сервис `email`** (2026-10-27): `auth` не
  зависит от скорости и доступности почтового провайдера, `email`
  масштабируется по очереди. Отброшена синхронная отправка из `auth`.
- **Challenge и лимиты — в Dragonfly, а не в Postgres** (2026-10-27): они
  живут минуты и умирают по TTL. Dragonfly работает в режиме кэша и может
  вытеснить ключ — тогда пользователь запросит код заново.
- **Ошибки — конверт `{"error": {...}}` из контракта продукта**
  (2026-10-27) вместо `application/problem+json`: у всех сервисов за
  gateway одна форма ошибки.
- **Постоянный пул 10 соединений без pre-ping и без PgBouncer**
  (2026-10-29). Замер: `/me` + `refresh` 400/с на один под. Пул 5 +
  overflow 5 открывал и закрывал ~990 соединений в минуту — это половина
  CPU Postgres (0,12 ядра против 0,06); постоянный пул на 10 — ноль новых
  соединений при тех же задержках. `pool_pre_ping` удваивал число
  транзакций (пинг на каждую выдачу соединения); без него CPU пода auth
  меньше на ~8%, Postgres — на ~20%. Цена — после обрыва всех соединений
  (рестарт Postgres) один запрос получает 503 `db.unavailable`: SQLAlchemy
  по первому обрыву сбрасывает весь пул. PgBouncer в режиме transaction
  отброшен: нагрузку на Postgres снимает так же, как постоянный пул, но
  добавляет свой CPU (0,06–0,1 ядра) и сетевой переход (медиана при
  400/с 13 мс против 4,5 мс) и не пропускает `statement_timeout` и
  `lock_timeout` из параметров подключения. Он понадобится, когда
  соединения всех сервисов и подов подойдут к `max_connections`.
  Узкое место пода — CPU процесса Python, а не БД.
- **`gc.freeze()` после старта, пороги GC по умолчанию** (2026-10-29).
  Замер 250/с через Traefik, трейсинг 100%: время в сборках мусора за
  прогон 1668 → 127 мс, паузы event loop >30 мс 53 → 6, 503 351 → 20,
  p99 `/me` 154 → 63 мс. Отброшено повышение порога молодого поколения
  до 10000: сборки реже, но длиннее — хвосты хуже (p99 до 351 мс).
- **uvloop и httptools** (2026-10-29): обе библиотеки — C-реализации цикла
  и разбора HTTP, uvicorn берёт их сам. CPU пода 0,58 → 0,55 при тех же
  хвостах.
- **Трейсинг 100% остаётся** (2026-10-29): после `gc.freeze()` он стоит
  ~15% CPU и не даёт 503; head-сэмплирование 10% почти не экономит CPU, а
  теряет трейсы ошибок, которые сохраняет хвостовое сэмплирование в Alloy.
  Отказ от спанов SQLAlchemy и Redis экономит ~0,03 ядра ценой
  невидимых запросов к БД и кэшу — отброшен. Убраны только спаны
  `receive`/`send`: на запрос их несколько, смысла в них нет.
- **Предел 64 одновременных запроса на под вместо 32** (2026-10-29). Замер
  разгона до 600/с через Traefik, KEDA 2–3 пода: 503 — 3024 против 8767
  (2,4% против 6,5%), p95 при перегрузке ~350 мс против ~260 мс. Ниже
  ёмкости подов разницы нет. Отказ на пике хуже лишних 100 мс ожидания.
- **Liveness с таймаутом 3 с** (2026-10-29): при 1 с перегруженный или
  ждущий диск под проваливал `/health` и перезапускался под нагрузкой —
  оставшимся доставалось больше, и отказы шли каскадом (замер старой
  версии: в пике готов 1 под из 3). Readiness остаётся строгой: выводит
  под из балансировки, не убивая его.
- **Минимум 2 пода** (2026-10-29): замер с одним подом — его удаление под
  нагрузкой ~60/с дало ~20 с ответов 5xx, пока поднимался новый; с
  несколькими подами трафик переходит на оставшиеся. Цена — ~125 МиБ и
  100m `requests` второго пода.
- **Гибкость вместо ресурсов** (2026-10-25): на одной ноде живёт до ~12
  сервисов, поэтому у пода дешёвые `requests`, предел одновременных
  запросов и автоскейлинг KEDA 1–3 по нагрузке. Прежние схемы — HPA 1–4 по
  CPU и один под в жёстких рамках — отброшены.

- **Версия в пути перед сервисом: `/api/v1/auth`** (2026-10-25). Так
  требует контракт продукта, фронт получает ровно описанные адреса.
  Отброшен вариант `/api/auth/v1`: кука refresh на `/api/auth` пережила бы
  смену версий, а Ingress не менялся бы, но это расхождение с контрактом.
  Цена выбора — переходный период для куки при v2, см. «Версии API».
- **JWKS без версии и вне `/api`** (2026-10-25): его читают только сервисы
  внутри кластера, браузеру он не нужен; формат JWKS задан RFC 7517 и
  версией API не меняется.

## Чего пока нет

- Rate limit по IP клиента: на маке Traefik видит у всех запросов адрес
  балансировщика k3d, поэтому лимит общий на всех.
- Сессий для сервисов (service identity) — см.
  [requirements.md](requirements.md).
